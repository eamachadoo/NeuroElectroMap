# Testing the Pipeline with Your Own Dataset

This guide describes how to run NeuroElectroMap end-to-end against a
patient that is *not* one of the bundled samples (MNE sample,
ds004473 sub-1/2/12). It covers what files you need to have, where
to put them, the exact commands to run, how long it takes, how to
read the outputs, and how to recover from the three failure modes you
are most likely to hit.

If you only want to verify that the pipeline runs against a known
dataset, follow the README's quick-start (`make data-ds004473 && make
run-ds004473`) instead — that path is fully automated.

---

## 1. What you need before you start

The pipeline takes three input categories:

| Input | Required? | Format | Notes |
|---|---|---|---|
| Pre-operative T1w MRI | **Yes** | `.nii` or `.nii.gz` | Single 3D volume in scanner-RAS. Diagnostic or surgical-planning T1 both work |
| Post-operative CT | **Yes** | `.nii` or `.nii.gz` | Single 3D volume. Diagnostic CT recommended; intra-operative O-arm CT is supported but the registration residual is larger (see [`VALIDATION_FINDINGS.md`](VALIDATION_FINDINGS.md) §9) |
| FreeSurfer reconstruction of the same T1 | **Yes** | FreeSurfer subject directory | Generated by `recon-all` — see §2 below |
| Ground-truth electrode positions | Optional | BIDS `*_electrodes.tsv` or NeuroElectroMap JSON | Only needed if you want the `--validate` step to report localisation error |

### 1.1 The FreeSurfer prerequisite

This is the single hard cost of testing with a new patient. The
pipeline reads the patient-specific surfaces and atlases that
FreeSurfer's `recon-all` produces; there is no shortcut.

If the patient already has a FreeSurfer recon (typical in any
clinical neuroimaging lab), skip to §2. If not, run:

```bash
# inside a FreeSurfer-enabled environment (FREESURFER_HOME set, license file present)
export SUBJECTS_DIR=/path/to/freesurfer/subjects
recon-all -i /path/to/patient_T1w.nii.gz -s patient_id -all
```

This takes **6–12 hours on a modern CPU per patient**. A faster
alternative is **FastSurfer** (deep-learning replacement for the
slow surface-recon steps), which produces a compatible directory in
~10 min on an NVIDIA GPU or ~1 h on CPU — see
<https://github.com/Deep-MI/FastSurfer>. FastSurfer's output drops
into the same `SUBJECTS_DIR` and the pipeline reads it without
modification.

## 2. What the pipeline reads inside `SUBJECT_DIR`

`SUBJECT_DIR` must point at the FreeSurfer patient directory (the
`<subject_id>` folder inside `SUBJECTS_DIR`). The pipeline reads
exactly these files:

```
SUBJECT_DIR/
├── surf/
│   ├── lh.pial                         # left  pial surface (mesh)          [required]
│   └── rh.pial                         # right pial surface (mesh)          [required]
├── mri/
│   ├── T1.mgz                          # FreeSurfer-conformed T1 volume     [required]
│   ├── aparc+aseg.mgz                  # Desikan-Killiany + subcortical seg [required]
│   └── transforms/
│       └── talairach.xfm               # native → MNI Talairach affine      [required]
└── label/
    ├── lh.BA_exvivo.annot              # left  Brodmann surface annotations [required]
    ├── rh.BA_exvivo.annot              # right Brodmann surface annotations [required]
    ├── lh.aparc.annot                  # left  Desikan-Killiany surface     [optional*]
    └── rh.aparc.annot                  # right Desikan-Killiany surface     [optional*]
```

\* `aparc.annot` powers the per-vertex lobe colouring in the 3D
viewer. If absent the cortex falls back to a neutral grey for
vertices outside the sparse BA_exvivo labels; the pipeline still
runs.

Before running, verify all four required files are present:

```bash
ls "$SUBJECT_DIR"/surf/{lh,rh}.pial \
   "$SUBJECT_DIR"/mri/{T1.mgz,aparc+aseg.mgz} \
   "$SUBJECT_DIR"/mri/transforms/talairach.xfm \
   "$SUBJECT_DIR"/label/{lh,rh}.BA_exvivo.annot
```

If any of these is missing, the pipeline will exit with
`FileNotFoundError` on the missing path — see Troubleshooting §6.1.

## 3. Running the pipeline against your patient

The minimum invocation only needs the three input volumes:

```bash
make run \
  MRI=/path/to/your/T1w.nii.gz \
  CT=/path/to/your/post_op_CT.nii.gz \
  SUBJECT_DIR=/path/to/freesurfer/subjects/patient_id
```

This runs the full pipeline (registration → segmentation →
brain-shift correction → cortical and volumetric labelling → CSV
report → viewer bundle), prints a phase-by-phase log to stdout, and
writes:

```
outputs/
├── reports/electrode_report.csv        # one row per detected contact
├── figures/electrodes_3d.png           # static 3D render
├── processed/
│   ├── mri_masked.nii.gz               # brain-masked T1
│   └── ct_registered.nii.gz            # CT aligned to T1
└── viewer/
    ├── manifest.js                     # patient list for the viewer
    └── patient_id/data.json            # per-patient bundle
```

To validate against ground-truth electrode positions, add `--validate`:

```bash
.venv/bin/python main.py \
  --mri         /path/to/your/T1w.nii.gz \
  --ct          /path/to/your/post_op_CT.nii.gz \
  --subject-dir /path/to/freesurfer/subjects/patient_id \
  --validate    /path/to/your/electrodes.tsv \
  --output-dir  outputs/patient_id_validated
```

The pipeline auto-detects whether the TSV is in metres or
millimetres via the BIDS `*_coordsystem.json` sidecar and reports
mean / max Euclidean error per contact using the shaft-aware matcher
described in [`PIPELINE_DESIGN.md`](PIPELINE_DESIGN.md) §4.4.

## 4. Expected runtime and output

On a 2024-class laptop CPU, with a FreeSurfer recon already
available:

| Phase | Time |
|---|---|
| Data preparation (NIfTI load, brain mask) | ~10 s |
| CT→MRI registration (rigid MI, dipy) | ~30–60 s |
| CT electrode segmentation (HU threshold + CCA) | ~5 s |
| Brain-shift correction (KD-tree on pial) | ~2 s |
| Cortical + volumetric labelling | ~5 s |
| Validation (if `--validate`) | <1 s |
| Viewer export (mesh decimation + JSON) | ~10 s |
| **Total (no recon)** | **~1–2 min** |

If you supplied a fresh patient and had to run `recon-all`, add the
6–12 hours from §1.1 once.

To view the result after `make run`:

```bash
make viewer    # serves at http://localhost:8765/
```

Your patient appears in the top-bar dropdown together with any
previously processed cases.

## 5. Reading the outputs

### 5.1 `reports/electrode_report.csv`

One row per detected contact, with columns: electrode ID, X/Y/Z in
mm, Brodmann area, anatomy label, brain-shift correction distance.
Opens directly in Excel or LibreOffice.

### 5.2 Console output during validation

When `--validate` is set you will see one line per ground-truth
contact:

```
  GT LENT4 → pred E83: 6.058 mm  [LENT]
  GT LPC2  → pred E107: 1.082 mm [LPC]
  ...
Mean Euclidean Error : 8.504 mm
Max  Euclidean Error : 26.891 mm
Unmatched GT contacts: 99 / 119 (LPLNIN1, ...)
```

The clinical target is mean error < 2.0 mm.

**Important — a high mean error does not automatically mean the
pipeline is wrong.** It can mean three different things:

1. **Genuine matches at sub-2 mm with high mean due to bad cases.**
   Look at the per-contact list: if you see several GT contacts at
   1–3 mm and a handful at 20+ mm, the registration is correct
   *somewhere* and the high mean comes from the rest.
2. **Many unmatched contacts.** If `Unmatched GT contacts` is high,
   the registration is regionally off by more than the shaft-axis
   search radius (10 mm by default). This is what we see on the
   ds004473 sub-12 O-arm CT — see [`VALIDATION_FINDINGS.md`](VALIDATION_FINDINGS.md).
3. **All contacts ≥10 mm with monotonic shaft IDs.** Indicates a
   global rigid registration offset that the MI metric could not
   recover (the metric peaks at a non-geometric optimum). The
   roadmap entry for this is bbregister — `VALIDATION_FINDINGS.md`
   §9.1.

### 5.3 Viewer

Use `make viewer` then click your patient in the top-bar. The 3D
view colours each pial vertex by its anatomical lobe; the 2D view
groups contacts by Brodmann region with a "Deep / non-cortical"
pool below for depth electrodes that have no surface label.

## 6. Troubleshooting

### 6.1 `FileNotFoundError` on a file under `SUBJECT_DIR`

The FreeSurfer recon is incomplete. Re-run `recon-all -s patient_id
-all` (or `-make all`) and verify §2's `ls` command lists every
required file before retrying.

Specifically:

| Missing file | Likely cause | Fix |
|---|---|---|
| `surf/lh.pial`, `surf/rh.pial` | recon stopped at `-autorecon1` | Run `recon-all -s patient_id -autorecon2 -autorecon3` |
| `mri/aparc+aseg.mgz` | recon stopped before `mri_aparc2aseg` | Same as above |
| `label/lh.BA_exvivo.annot` | recon was run without `-balabels` | Run `recon-all -s patient_id -balabels` (~30 min) |
| `label/lh.aparc.annot` | recon was run without `-cortparc` | Run `recon-all -s patient_id -cortparc` (~10 min); optional, falls back to grey in 3D viewer |
| `mri/transforms/talairach.xfm` | recon-all skipped Talairach step | Run `recon-all -s patient_id -talairach` |

### 6.2 Pipeline prints many `[WARNING] Electrode N: large brain-shift correction NN mm`

The CT→MRI registration has a large residual error, or your patient
has electrodes well outside the cortical surface (depth electrodes
in subcortical structures). The first is a registration problem; the
second is normal and the pipeline handles it via the volumetric
ASEG labelling.

Quick check: open `outputs/processed/ct_registered.nii.gz` and the
input T1 in any NIfTI viewer (FreeView, MRIcron, ITK-SNAP). If
visible structures (skull outline, ventricles) overlay correctly,
the registration is OK and the warnings are about depth contacts.
If structures are visibly misaligned by more than a few millimetres,
see §6.3.

### 6.3 Mean validation error >> 2 mm

Read the per-contact list. If errors cluster tightly within each
shaft but the magnitudes are large (15+ mm), the registration is
landing on a non-geometric MI optimum — exactly the failure mode
documented in [`VALIDATION_FINDINGS.md`](VALIDATION_FINDINGS.md).
This is intrinsic to the current MI-based rigid registration on
certain CT/MRI pairs (notably intra-operative O-arm CTs); the
documented next step is `bbregister`. There is no parameter to tune
that would close this gap.

If the errors are *not* tight within shafts and look random, the
matcher is failing for a different reason — most likely the GT TSV
is in a different coordinate frame than the predicted electrodes.
Check the BIDS `*_coordsystem.json`: the GT must declare
`iEEGCoordinateSystem: ScanRAS` and `IntendedFor:
…/anat/<subject>_T1w.nii.gz`.

### 6.4 Viewer shows electrodes in the wrong hemisphere

This is the classic mirrored-anatomy bug — usually means the input
NIfTI is in LPS, not RAS+, and the loader's reorientation step
failed to detect it. Verify with:

```bash
.venv/bin/python -c "import nibabel as nib; print(nib.aff2axcodes(nib.load('your_T1.nii.gz').affine))"
```

The output should be `('R', 'A', 'S')`. If it is not, the file was
not produced by `dcm2niix` or has been re-encoded with the wrong
header; re-export from the original DICOM with `dcm2niix -1` (single
volume, RAS).
